0. The big idea (what the tutor spent the class on)

Policy Iteration is our first real RL algorithm. It finds the optimal policy (the best action to take from each state) for a fully-known MDP. The tutor kept repeating one thing: this is a two-step process run in a loop — Policy Evaluation then Policy Improvement, alternating until the policy stops changing.

Pick a policy
any policy, even random
→
1. EVALUATE
compute V_π (how good is this policy?)
→
2. IMPROVE
be greedy: pick best action per state
→
Policy changed?
yes → loop again
Stopping rule: when the new policy == previous policy, there is no more room to improve → we've reached the optimal policy. We match on the actions a policy recommends, not on the value numbers.

1. Policy Evaluation — "how good is this policy?"

First half of the algorithm (the tutor called it the prediction problem). Input: a policy π (any policy — often random to start). Output: the state-value function V_π, which says how good it is to be in each state while following that policy.

V_π(s) = Σ_s' P(s'|s, π(s)) · [ R(s, π(s), s') + γ · V_π(s') ]

For a deterministic policy (each state chooses one action), π(s) gives the action directly, and the equation simplifies.

How it works internally (the iterative loop)

  1. Initialize V(s) = 0 for every state.
  2. For each state, get the action from the policy (the policy is fixed — we never touch it here).
  3. For that chosen action, look up the transition probabilities P(s'|s,a) and the reward R, and compute the Bellman backup: transition_prob × (reward + γ·V(next)).
  4. Update V(s) with that value; track the largest change Δ.
  5. Repeat until Δ < θ (a small threshold, a hyperparameter like γ — the tutor stressed there's no right answer, you pick it).
Key mental model (from the tutor): the recursion works because we always know the next state's value (V_π(s')), but not the current one — so V(s') starts at 0 and gets built up iteration by iteration. We can do this because "we know the next state, not the current one, that's why the value is initialized to zero."

Important: policy evaluation does not require the argmax and does not change the policy. It only follows the given policy and returns better V values.

2. Policy Improvement — "can we do better?"

Second half (the control problem). Input: the value function V computed by Policy Evaluation. Output: an improved (greedy) policy.

π'(s) = argmax_a Σ_s' P(s'|s, a) · [ R(s, a, s') + γ · V(s') ]

For each state, for each possible action, compute the action-value Q_π(s,a) using V from step 1, then pick the action with the highest Q value:

Q_π(s,a) = Σ_s' P(s'|s, a) · [ R(s, a, s') + γ · V(s') ]
V vs Q (the tutor's wording): "V_π is how good is that state following this policy. Q_π is how good is the action — but taken from that particular state." V judges the state; Q judges the action so we can pick the best one.

Two important nuances the tutor pointed out:

  • Policy Improvement does NOT need a starting policy. It builds a brand-new policy from scratch using the V values (which came from Policy Evaluation). Only Evaluation needs a policy to follow.
  • Deterministic vs stochastic: in the drone MDP, each action leads to the next state with probability 1, so "argmax" collapses to just picking the single best action — no probability weighting needed. In FrozenLake (Part 2), actions are probabilistic (pushing a direction only sometimes works), so the argmax over the weighted Q values becomes essential.

3. Policy Iteration — the full loop

The orchestrator that alternates the two steps until convergence. The tutor emphasized it's literally just "a while True loop alternating between evaluation and improvement, breaking when new policy == previous policy."

Random init
V=0, any π
→
EVALUATE
V_π via Bellman backup
→
IMPROVE
π' = argmax over Q
→
π' == π?
yes → done, π is optimal

It returns two things: the optimal value function V and the optimal policy π. The tutor stressed: because an MDP's environment is fully known (transition probs + rewards + actions + γ), the algorithm is guaranteed to reach the optimal policy — if it didn't, "there's no meaning to the algorithm."

Recognize the code mapping (used in both notebooks):
  • policy_evaluation(...) / compute_policy_v(...) → the EVALUATE step (Bellman backup loop).
  • policy_improvement(...) / extract_policy(...) → the IMPROVE step (argmax over Q).
  • policy_iteration(...) → the outer while loop that alternates them.

4. Part 1 — Drone Package Delivery MDP (hand-implemented)

The case study: a delivery drone moves between zones W (Warehouse), A, B, C. States = current location; Actions = fly to W/A/B/C.

The setup

  • States: {W, A, B, C}
  • Actions: {Fly_W, Fly_A, Fly_B, Fly_C}
  • Transition matrix: deterministic cycle W→A→B→C→W:
    W:[0,1,0,0] A:[0,0,1,0] B:[0,0,0,1] C:[1,0,0,0]
    So e.g. P(W→C) = 0, P(W→A) = 1 (only one action possible from W, the tutor walked through reading these probabilities).
  • Reward matrix: reward for taking each action from each state:
    W:[0, 10, -4, -6] A:[-2, 0, 10, -3] B:[-3, -1, 0, 10] C:[10, -3, -2, 0]
    (columns = Fly_W, Fly_A, Fly_B, Fly_C). So from W, flying to A gives +10, flying to B gives −4.

The policy is the full cycle: W→A→B→C→W, flying to each next location to grab its +10 reward. The value function V reflects that: C has the highest value (+10) because it can immediately reach the reward.

Tutor tip: the initial policy is random — you can change it inside policy_iteration and the algorithm still converges to the same optimal policy. That's the point: the MDP dynamics (known) drive the answer, not the starting policy.

5. Part 2 — FrozenLake in OpenAI Gym

Same algorithm, but the environment (transition probabilities, rewards) comes from an OpenAI Gym environment instead of hand-written matrices. The tutor set up FrozenLake-v1 with video rendering.

env = wrap_env(gym.make('FrozenLake-v1', new_step_api=True))
  • Action space: Discrete(4) — {Left, Down, Right, Up}
  • Observation space: Discrete(16) — a 4×4 grid, 16 states.
  • Key difference from the drone: the tutor stressed FrozenLake moves are probabilistic — pushing a direction doesn't always succeed. "From a particular state there are different probabilities of going up, down — there is not a single action." That's why argmax over Q becomes essential (you must average over successor states).

Mapping the algorithm onto the environment

  • compute_policy_v(env, policy, gamma) → Policy Evaluation. Iterates V(s) using env.P[s][action] (the environment's transition + reward + done info) until convergence (epsilon ~1e-10).
  • extract_policy(v, gamma) → Policy Improvement. Computes Q for all 4 actions per state, takes argmax of Q → new policy. "QSA is our action value, and we take the argmax of the action value."
  • policy_iteration(env, gamma) → the outer loop. Initializes a random policy, loops compute_v → extract, stops when the policies match (np.all(policy == new_policy)).
  • evaluate_policy / run_episode → evaluation, not Policy Evaluation. The tutor cleared this up: this measures how good the final policy actually is by running episodes and averaging total reward. An episode = one complete run of states from start to terminal state (the "one complete path from here to the goal, then it restarts").

6. Assignment 1 guidance (from the tutor)

The tutor spent time explaining what assignment 1 expects. You will be given a scenario (e.g. an autonomous navigation system) and must:

  1. Design your own MDP: define the states, the actions available from each state, and draw a state-transition diagram.
  2. Define the transition matrix and reward matrix from that diagram.
  3. Run Policy Iteration to get the value function and policy.
  4. You cannot use gymnasium for assignment 1 — you hand-define the MDP (like Part 1, not Part 2).
"There is nothing called best accuracy, best policy, or optimal policy here." Any policy you get is fine — what matters is that you logically explain WHY you chose your transition-matrix values and reward-matrix values (e.g. why a particular transition has probability 0.7, why a penalty is −4). "If you can properly explain why, you'll get full marks." Depth of reasoning beats the numbers themselves — just like in deep learning, don't chase accuracy.

7. Study advice & key takeaways

What the tutor emphasized

  • Don't miss lectures. This course is math-heavy ("starting from this week, it's really really hard if you don't understand this part").
  • Rewrite the formulas by hand (pen and paper). "Start from R(t+1), the expected value of G_t... rewrite the formula and it will never leave your head." Follow Sutton & Barto (the book, free — see your reading list) for the derivations.
  • Blindly coding the formulas is fine for the implementation, but you must understand the theory for MDPs — learn the terminology: what V_π(s) is, what each term in the Bellman equation does.
  • Theta (θ) is a hyperparameter just like γ ("no hard rule... based on what you decide"). γ ∈ [0,1]: increase γ → rely more on future/delayed rewards; γ=0 → only immediate reward.
  • Don't mix RL jargon with deep-learning intuition. The tutor specifically said: don't relate anything from deep learning to RL. E.g. "evaluate_policy" here is NOT the Policy Evaluation step — it's testing the finished policy by running episodes, analogous to plotting learning curves.
  • Next week: Value Iteration — "you'll see the difference between policy iteration and value iteration next week, then everything will be clear."

Checklist — can you explain these?

  • What does V_π(s) measure, and why is it an expectation?
  • Why does the current state's value depend on the NEXT state's value (recursion)?
  • The two steps of Policy Iteration, and why Improvement needs no starting policy but Evaluation does.
  • Why deterministic MDPs skip the probability weighting (argmax still there, just over one action).
  • Why FrozenLake needs the argmax over Q, unlike the drone MDP.
  • When the overall algorithm stops, and what it returns.
